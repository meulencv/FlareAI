# Custom tests

> Create test cases with expected conversation flows and tool calls

Custom tests — labeled **Prompt** tests in the platform — let you define specific conversation scenarios and validate that your agent responds correctly. Each test specifies a sequence of messages, optional expected tool calls, and evaluation criteria — either a custom LLM judge prompt or northstar-based grading.

## The Tests page

Every test for a workflow lives on one page: open a workflow and go to **Evals > Tests**. Prompt tests (described on this page) and adversarial tests share it, so you no longer switch between separate **Custom Tests** and **Adversarial** pages.

| Control                        | What it does                                                                                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Search**                     | Filters by test, prompt, or agent name.                                                                                                                                                                |
| **All / Prompt / Adversarial** | Filters by test type. Each toggle shows how many tests it holds. Types you don't have permission to view aren't offered.                                                                               |
| **View toggle**                | Switches between the flat list (the default, with a breadcrumb on each row showing which agent and prompt it belongs to) and a tree grouped by workflow structure via **Group by workflow structure**. |
| **New**                        | Creates a **Test** (then choose **Prompt** or **Adversarial**), a **Suite**, or a **Folder**.                                                                                                          |

Run a single test from its row or its panel with the **play button**, or use the page's **Run** menu to start **All tests** or **Selected tests** against the version you have selected.

### Folders

Folders organize tests of any type — a folder can hold prompt tests and adversarial tests side by side. Create one from **New > Folder**, then move tests into it from a test's row menu.

Tests that aren't in a folder are listed outside the folders rather than hidden in an "unfiled" bucket. When a type filter is active, folders with nothing matching it are hidden so the list stays short.

## Creating a test

<Steps>
  <Step title="Open the Tests page">
    In the workflow editor, go to **Evals > Tests**.
  </Step>

  <Step title="Create a prompt test">
    Click **New > Test** and choose **Prompt**. A new test form opens with default variables loaded from your workflow.
  </Step>

  <Step title="Select the prompt node">
    Choose which prompt node (agent) this test applies to from the dropdown at the top.
  </Step>

  <Step title="Build the conversation">
    Add messages turn by turn to create the test conversation:

    * **User messages** — What the simulated user says
    * **Assistant messages** — What you expect the agent to say (the last assistant turn is generated by the agent during evaluation)
    * **Tool calls** — Tool invocations and responses that should appear in the conversation

    Use the hover actions on each message to edit, delete, change role, or add messages between existing turns.
  </Step>

  <Step title="Set evaluation criteria">
    Choose an **evaluation mode**:

    * **Custom** — Write criteria describing what a correct response looks like. An LLM judge evaluates the agent's output against your criteria. You can also select which **judge model** runs the evaluation from the model dropdown.
    * **Northstar** — Select one or more northstars. The agent's response is graded against each selected northstar using the standard audit process.
  </Step>

  <Step title="Configure expected tool calls (optional)">
    If the agent should call specific tools, add **expected tool calls** with:

    * **Function name** — The tool that should be called
    * **Argument descriptions** — What each argument should contain (described in natural language for the LLM judge)
  </Step>

  <Step title="Set test variables">
    Override workflow variables for this test. Variables are key-value pairs that get injected into the prompt during evaluation — useful for testing behavior with different data inputs.
  </Step>

  <Step title="Save and run">
    Save the test, then click the **play button** to execute it.
  </Step>
</Steps>

## Running tests

When you run a test, the system:

1. Sends the test conversation to the agent (all messages up to the last user turn)
2. The agent generates a response
3. The LLM judge (or northstar auditor) evaluates the response against your criteria
4. Results appear in the conversation canvas with a **judge result card**

The judge result shows:

* **Passed/Failed** status with color coding (green/red)
* **Judge reasoning** — Why the response was evaluated this way
* **Tool call matching** — Whether actual tool calls matched expected tool calls

Remarks from northstar-graded tests accept [audit feedback](03-Automated-audits.md#audit-feedback) like any other remark. Mark a scenario grade as accurate or inaccurate from the northstar audit table, and attribute an inaccurate grade to the auditor or to the northstar itself.

## Judge model

When using the **Custom** evaluation mode, you can choose which LLM model evaluates the agent's response. The judge model reads your criteria and reasoning, and returns a pass/fail decision with an explanation.

Select a model from the **Judge Model** dropdown in the evaluation criteria panel. When no selection is made, judging runs on [GPT-5.6 Luna](../14-Assets/05-Models.md#gpt-5.6-luna) — priced for the volume that eval suites generate. Pick a larger model, or raise the reasoning effort, when your criteria need deeper deliberation than the default provides.

<Note>
  Judge models always run at standard speed — the **Fast** priority tier isn't offered here.
</Note>

## Adding examples

You can add success and failure examples to improve judge accuracy:

* **Success examples** — Sample responses that should pass
* **Failure examples** — Sample responses that should fail

These examples give the LLM judge additional context for borderline cases.

## Extracting tests from runs

Instead of building conversations from scratch, you can create tests from existing run transcripts. This is useful for:

* Capturing a known-good conversation as a regression test
* Creating a test from a failed run to prevent the same issue from recurring
* Building a test suite from representative production conversations

## Execution history

A test's panel has two tabs: **Overview**, which shows the test's conversation, criteria, and variables, and **Executions**, which lists every run of that test with a count beside the tab label. Each entry shows:

* Status — **Passed**, **Failed**, **Queued**, **Running**, **Canceled**, or **Error**
* When the test ran
* Which version was tested

The history loads more entries as you scroll, and the filter button limits it to the current version or to failed executions only. Click an execution to view the full conversation and judge reasoning. Recent executions also appear inline on the test's row in the table.
